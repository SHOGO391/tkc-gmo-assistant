# 次の実機検証手順

P1の次は、実TKC・GMOの**読取り確認**を進めます。登録・計上・対象外化・締め操作は、対象と方法を確認し、利用者の実行承認を得てからP2で実装・検証します。

導入目標は、Computer Useで取込み・計上まで実行し、不明点を人へ引き継ぐ運用です。現在はブラウザ操作のみ利用可能です。ブラウザ版ならChromeでTKCへログインし、Windowsアプリ版ならネイティブ操作が有効な環境を用意してから観察します。実機未接続の間は実TKCへの書込みを追加しません。[引継ぎ機能と導入の順序](human-handoff.md)

## 1. 対象と証跡を確定する

利用者にTKCの製品名・バージョン、対象ブラウザ・プロファイル、対象会社・GMO口座・同一月内の期間、閲覧権限、未締め状態を確認します。ログインは利用者が行います。パスワード・トークンを記録しません。

Computer Useで実画面を観察し、会社・口座・期間・締め状態・ログイン状態・権限がどこで分かるかを記録します。匿名化前の画像・CSV・画面契約はGit対象外へ保存します。画面の保存操作は行いません。

製品名を確定した後、銀行信販データ受信の利用状況と、仕訳ファイル・取引先一覧の読込メニューを読取り範囲で確認します。製品の連携機能が利用できるなら、確認済みの案をその経路に渡す設計を優先します。公開資料で確認した候補は [P0記録](P0-environment.md#fxシリーズの入力省力化経路2026-10-09) に記載しました。接続設定の変更、連携の申込、試験ファイルの取込もこの読取り確認では行いません。

## 2. 実CSVの読み取りを検証する

1. GMOの元ファイルをそのまま取得し、CSV種類、文字コード、ヘッダー行、前置き・末尾行、日付、入出金列、空欄とゼロ、残高、通貨を確認します。
2. 明細IDがある場合、期間を重ねた2つの出力で同じ取引のIDが一致するか確認します。連番や出力ごとに変わるIDなら、安定IDとして使いません。
3. TKC一覧を読取り・出力し、コード、正式名称、カナ、所在地、法人番号、登録番号、必須項目と空欄を確認します。コードは数値に変換しません。
4. P1に「実データ」ジョブを作成し、列対応を手動設定します。原本の行数・入金合計・出金合計・不正行・明細ごとの値・SHA-256・物理行位置を突き合わせます。
5. 同じ原本、重複期間、同日同額の別取引、IDなし同一内容を取り込みます。実取引を消さず、再利用または要確認になるかを確認します。

初回は匿名化した実CSVで確認し、匿名化で日付・金額・ID・同一会社の関係・先頭ゼロが変わっていないことを確認します。ヘッダー重複や独自の集計行等に現実の形式が対応しない場合、実ファイルを根拠にパーサーを拡張します。

## 3. 読取りアダプタを接続する

`src/adapters.ts` の `TkcReadAdapter` を実製品に合わせて実装します。既存の `PlaywrightReadAdapter` は観察済みの画面契約を渡して会社・口座・ログイン・未締め月を確認する枠組みで、実TKCのセレクタはありません。現在の標準サーバーは `UnconnectedTkcAdapter` です。

セレクタは実画面で確認したものを使用し、観察日・根拠・許可URLを記録します。ログイン切れ、誤会社・誤口座、締め済み、権限不足、画面変更を読み取り範囲で試し、確認できない場合は利用不可として止めます。未締め月の取得方法が既存の契約と違う場合、実画面に合わせて交換します。

過去仕訳と受信銀行明細についても、取得日・対象範囲・取得成否・取得した全比較項目を保存できる読取りインターフェースを追加します。取得失敗を空の一覧に変換しません。手動入力・他ファイル経由・受信済み明細との一致、不一致、複数候補を検証します。

## 4. 取引先と仕訳の案を実データで確認する

請求書・契約書・法人情報等で既存先を確認します。振込カナだけでは確定しません。新規先は正式名称・所在地・法人番号・必要なら登録番号を項目ごとの出典と一緒に確認します。番号未確認・個人事業者・同名別法人は保留し、P1の法人番号必須条件を無理に回避しません。

同じ法人の複数明細が1つの登録案になり、別法人が混ざらないことを確認します。候補コードは最新マスタで衝突確認します。仕訳案は科目・口座対応・税区分・摘要・手数料・相殺・分割を担当者が確認し、根拠付きルールとして設定します。複数ルールの競合は保留します。

## 5. P2へ進む条件と検証

P0の製品・画面・CSV・権限・会社口座・締め・保存結果取得・同時操作の確認がそろったら、実行対象の登録案と仕訳計画を提示して承認を得ます。P1でのプレビュー承認はTKC書込みの承認として流用しません。

P2では次の処理を追加してから、小さい検証対象で試します。

1. 計画と行ごとのハッシュを直前に再検証する。変わった行だけ再確認に戻す。
2. 会社・口座・月・権限・締め・既存仕訳・他担当者の操作を確認する。ローカルDBのロックだけではTKCとの排他はできない。
3. 外部書込み前に操作意図を永続保存する。取引先登録と仕訳計上に別の操作ID・状態を使用する。
4. 取引先登録後にマスタを再取得し、実際のコード・正式名称等を比較して確定する。中断しても同じ登録を再送しない。
5. 仕訳保存後に日付・金額・方向・口座・科目・取引先・税区分・摘要を読戻し、承認計画と照合する。完了メッセージだけでは確定しない。
6. 通信断を登録直後・計上直後に発生させる。結果不明ならunknownを保持し、実結果を照合する。0件・複数件・取得失敗は盲目的な再送を許可しない。
7. 10件中6件保存後に中断・再起動・バックアップ復元を行い、既存6件と残り4件を照合する。
8. 原本・アプリ・TKCを同じ対象範囲で集計し、銀行残高と純増減を確認する。未計上・結果不明が残る月を完了にしない。

その後、1か月100件以上・新規10社以上で操作時間と誤りを測定します。Jevは基本動作の完成後に、同じ対象・同じ確認条件で操作時間、精度、再開性、費用を比較します。
